# Перенос на ПК и последующее внедрение

## 1. Получить материалы без изменения рабочей версии

Открыть терминал в существующей локальной папке prompt-engineering-app. Сначала:

```bash
git status
git remote -v
```

Проверить, что origin — нужный репозиторий. Если есть несохранённые изменения, остановиться и сохранить их отдельным коммитом или осознанно убрать в stash; не выполнять reset --hard, checkout -- или clean.

Затем:

```bash
git fetch origin
git switch --create proposal/contest-v2-100 --track origin/proposal/contest-v2-100
```

Если локальная ветка с этим именем уже существует: перейти в неё через git switch proposal/contest-v2-100 и обновить git pull --ff-only, проверив рабочее дерево. Не пересоздавать ветку.

Открыть docs/proposals/contest-v2/README.md. Приложение остаётся на старых правилах.

## 2. Забрать только этот коммит в свою рабочую ветку

Вместо переключения на proposal-ветку можно перенести добавление материалов:

```bash
git fetch origin
git log --oneline origin/proposal/contest-v2-100
git cherry-pick <SHA-коммита-с-пакетом>
```

Выполнять в выбранной рабочей ветке при чистом git status. Использовать SHA именно коммита добавления пакета, а не всю ветку, если в ней позже появятся изменения.
При конфликте не затирать свои файлы: разобраться или отменить перенос git cherry-pick --abort.

Можно также открыть proposal-ветку на GitHub и скачать ZIP через Code → Download ZIP, затем скопировать только docs/proposals/contest-v2. Копирование не переносит историю Git.

## 3. Что требуется для настоящего включения

Не ограничиваться multiplier=1: session.py всё равно прибавит минуты и получится шкала до 110, а TaskPack останется старым.

| Компонент | Необходимое изменение |
|---|---|
| prompt_rules.py | Версионированная схема v2, веса 25+20+15+15+15+10, атомарные проверки и доказательства; не просто новые ключевые слова |
| tasks.json | Преобразовать согласованный draft в поддерживаемый формат; заменить только вместе с оценщиком |
| session.py | Убрать умножение и бонус минут для v2; максимум 100; новый идентификатор scoring_rule |
| settings.py / config.json | Явный выбор версии шкалы; не применять старый multiplier к v2 |
| ui/app.js / ui/index.html | Показ короткого условия вместе с общими правилами и шкалой; максимум 100; убрать описание бонуса |
| collect_results.py / ranking_excel.py | Валидация версии и диапазона 0…100; корректные подписи; рейтинг по баллам и времени |
| result_store.py | Проверить сохранение новых полей и версий; не переписывать старые результаты |
| README.md / RULES_README.md / NETWORK_SETUP.md | Описать новое поведение и переход между мероприятиями |
| tests/ | Тесты новой шкалы, границ, противоречий, таймера, интерфейса и экспорта |

Старые результаты сохранить читаемыми и явно версионированными. Не смешивать v1 и v2 в одном рейтинге; для нового конкурса использовать отдельный день/набор результатов. Версии оценщика и пакета, хеш пакета и правило подсчёта сохранять в попытке. Проверить, что старый сборщик не принимает новый формат молча.

## 4. Проверки перед публикацией

- Ручная проверка эталонов и нескольких пробных ответов для всех 30 заданий.
- Синонимы, перестановки фраз и краткие полные инструкции не должны несправедливо терять баллы.
- Ноль, частичные ответы, максимальный ответ, противоречия, ошибки и пустой автоответ.
- Максимум ровно 100, отсутствие бонуса за скорость, равенства мест.
- Нельзя заработать баллы простым повторением слов или несвязанными ключевыми словами.
- Сетевое сохранение, повторная отправка и старые записи не ломаются.
- Выполнить существующие Python/Node-тесты и добавить новые, затем проверить сборку на Windows.

## 5. Готовое задание агенту на ПК

> Прочитай корневой AGENTS.md, если он есть, Git status и docs/proposals/contest-v2/README.md, TASKS.md, SCORING.md, tasks.v2.draft.json и INTEGRATION.md. Работай в существующем prompt-engineering-app, не создавай новое приложение. Реализуй согласованные короткие задания и шкалу строго 0–100 без бонуса минут. Сохрани пользовательские изменения и старые результаты. Не заменяй tasks.json до поддержки схемы оценщиком. Показывай участникам все общие требования и критерии. Внедряй небольшими проверенными коммитами, обнови тесты и сборщик. Не публикуй секреты и результаты участников. Если надёжная офлайн-проверка какого-то критерия невозможна, явно обозначь ограничение и предложи ручной пересмотр, не имитируй смысловую оценку ключевыми словами.
